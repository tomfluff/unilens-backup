# Live: a spoken conversation in the chat

## Context

The builder's direction since 2026-09-24 is live interaction. They approved a first version over the OpenAI Realtime API and the Gemini Live API, with a Live button that works like the chat, and with the choices that could go either way as settings. Research: `.local/research/2026-09-27-realtime-apis.md` (private).

## Decision

- **A Live button next to the field.** Pressed, it starts a spoken talk about the page; pressed again, it ends it. Folded, the chat keeps the button while a talk is on.
- **Both sides' words come in as messages:** captions while speaking, then the final words.
- **The talk's state** (listening, hearing you, thinking, speaking) shows in the field while the chat is open, and on the status line when it is folded. Screen readers hear when it is the user's turn again.
- **Stopping works at any moment**, even while the talk is still connecting: its microphone and connection close as soon as they exist.
- **The model points at what it talks about.** A `highlight(ids)` tool lights the elements up and brings them into view, and the reply gets their source chips.
- **OpenAI Realtime over WebRTC.** The browser's offer goes to the backend (`POST /api/live/openai`), which starts the call with the session set there. No key or token reaches the page.
- **Gemini Live over a WebSocket**, opened with a one-use token (`POST /api/live/gemini`) that locks the session to what the backend sets. The reply plays through an `<audio>` element, which the browser's echo canceller hears. The talk carries on in a new connection when one ends (about every 10 minutes).
- **What the model knows** is the first user turn, as untrusted, delimited data: the clicked element, the page's inventory, the chat so far, and a small picture of the view. The rules stay in the session's instructions.
- **The text chat goes on from the talk.** Each finished turn joins the session's history (`POST /api/live/log`), and only a session that holds the capture takes it. Typing during a talk is part of it.
- **"Live interaction" settings:** provider (as the AI settings, OpenAI or Gemini), model, voice, how soon a pause ends a turn, stopping it by speaking over it, lighting up what it talks about, sending a picture of the view, captions while speaking, and the speaking rate (OpenAI).
- **Defaults:** `gpt-realtime-2.1-mini` with the voice marin, and `gemini-3.8-live` with Kore.

## Tried

A spoken question ("What do shareholders get? Can you show me where it says so?") through a fake microphone, on the SoftBank mirror:
- both providers answered correctly and lit up the right source;
- OpenAI's first words came about 1.3 s after the question.

## Known

- The models sometimes still say "let me check" first, or mention the highlight, although the rules ask them not to.
- Like the rest of the backend, the Live routes have no login: in a deployment, `GUARDRAILS=on` rate-limits them.

### From the second round of testing (2026-09-27)

- **Live sees where the user is.** When the user begins a turn (speaking or typing) and has scrolled or zoomed since the last picture, the widget renders what they see (about 1 s, the same html2canvas render as a capture, only the visible part) and sends it with a line saying where it is on the page. OpenAI's replies are now started by the widget (`create_response` off), after the picture, which they wait for at most 2.5 s; Gemini takes it as part of the turn. Chrome keeps the microphone's audio while the page renders (checked: nothing lost in a 1 s block), so the words are only late, not dropped.
- **Pointing no longer moves the page.** Lit things stay where they are, and the chat does not step aside for them. A new tool, `go_to(id)`, brings one element to the middle when the user asks ("take me there").
- **The numbers sit in the spoken words**, where the model was when it pointed: before the end of that sentence, or of the next when it pointed first; a sentence that names the element takes it.
- **"The second one" is number 2.** Each tool's result lists the reply's sources in the chat's numbering, and the rules say what the user means by it.
- **Gemini's captions keep only what it says.** Its transcript can carry text it never says (a tool call written out, an `<LMDX>` block, runs of `<br>`); the captions and the history drop it. `go_to`'s result is scheduled `WHEN_IDLE`, so a turn that was only the call still says something.
- Tried for real on the mirror: OpenAI `gpt-realtime-2.1` and `-mini`, Gemini `gemini-3.8-live`. The full OpenAI model took "take me to the second one" to source 2, and described the footer after the user moved there; replies began about 1.4 s after the user stopped.

### After the second round (2026-09-27)

- **Live gets the page again when it changes.** Before, a talk kept the elements of the capture it started with: after a click opened a tab, the model could not see or light what appeared. Now a click during a talk is followed, 0.5 s later, by a check of the page's elements (which elements they are, and their role, name and state, but not the containers around them, which regroup as the view scrolls; about 7 ms). If they changed, the page is captured again into the session, and the model gets the new inventory and close-up (`POST /api/live/page`) at once, without a reply, if no one is speaking. The talk then points with the new ids, and each reply keeps the capture it began on. An Alt+click on a new place sends that place the same way, and a question typed while it is captured waits for it. A change the click check missed is caught when the user next begins a turn. A page is sent once, even when a turn begins while it is being taken.
- **Typed follow-ups, too.** The chat's view refresh (`refreshCapture`) now also captures again when the page's elements changed, not only when the view moved.
- **Why not with the question:** Gemini garbles a question that the page lands in the middle of, because the words held meanwhile reach it all at once. Sending the page as soon as it changes avoids that when the user speaks 1.7 s or more after the click, which is how long the check and the capture take on the mirror.
- Tried for real on the mirror, a click on the "株主特典イベント・キャンペーン" tab and then two questions, on Gemini `gemini-3.8-live` and OpenAI `gpt-realtime-2.1-mini`. Both described the new tab, and both lit its FAQ entry, an id that did not exist in the first capture (it had been "※1").
